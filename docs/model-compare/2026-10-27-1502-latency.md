## เวลา 5.4 วินาทีหมดไปกับอะไร (วัดแยกบน Mac)

วัดตรงกับ Ollama ด้วย `build_messages` จริง (บทสนทนาต่อเนื่อง 3 ข้อ) และวัด `tts.synthesize` แยก

| ช่วง | เวลา | หมายเหตุ |
|---|---|---|
| อ่าน prompt จนได้ token แรก | 0.7–1.3s | ข้อแรก prefill 0.66s ข้อถัดไป ~1.27s (น่าจะอ่านคำตอบก่อนหน้าใหม่บางส่วน ดูข้อ 3 ด้านล่าง) |
| เขียนบรรทัดรับคำ `[concern]……はい。` | ~0.7s | ~7 token รวมแท็ก |
| เขียนประโยคเนื้อหาแรก `[concern]……お疲れです。…` | ~1.2–1.6s | บรรทัดเนื้อหาจบที่ 2.9–3.6s หลังส่ง |
| TTS (edge-tts) ประโยคเนื้อหา | 1.0–1.4s | `……はい。` ใช้ 0.65–0.9s · ระหว่างวัดมี `TTS failed ... th-TH-PremwadeeNeural` และ `TTS ok on attempt 2` บ้าง |
| ส่วนต่างที่เหลือในแอป | ~0.5–1s | ตัวอักษรแรกขึ้นจอในแอป 2.1s เทียบกับ token แรกตรงจาก Ollama 0.7–1.3s |

สรุป: **ทุกข้อไม่ผ่านเพราะ "บรรทัดรับคำของโมเดล + แท็ก + TTS ผ่านเน็ต" รวมกันเกิน 4 วินาที** ไม่ใช่เพราะโมเดลเขียนประโยคเนื้อหายาวเกิน (ประโยคเนื้อหาแรกสั้นตามกฎทุกข้อ)

### ข้อเสนอให้ผ่าน 4 วินาที (ฝั่ง Windows แก้)

1. **เลิกให้โมเดลเขียนบรรทัดรับคำ `……はい。`** เพราะเบราว์เซอร์เล่น ん。/はい。 ที่อัดไว้แล้ว บรรทัดนี้เลยซ้ำซ้อน และทำให้ประโยคเนื้อหาช้าไป ~0.7s
   ให้บรรทัดแรกเป็นประโยคเนื้อหาสั้นเลย (เช่น `[concern]……お疲れです。`)
2. **ลดแท็กอารมณ์:** แท็ก `[concern]` ใช้ 3–4 token (~0.35s) ต่อบรรทัด ใช้แท็กเฉพาะเมื่ออารมณ์เปลี่ยน หรือใช้ชื่อสั้น
3. **เช็ก prompt cache ระหว่างข้อ:** ข้อแรก prefill 0.66s แต่ข้อต่อๆ ไป ~1.27s ทั้งที่ข้อความใหม่มีแค่ไม่กี่สิบ token น่าจะเป็นเพราะ chat template ของ Qwen3 แสดงคำตอบเก่าของ assistant ไม่เหมือนตอนที่สร้าง (เช่น ส่วน `<think></think>`) cache จึงหลุดตั้งแต่คำตอบก่อนหน้า ถ้าแก้ได้จะประหยัด ~0.6s
4. **TTS เริ่มเร็วขึ้น:** ส่งประโยคเนื้อหาไป TTS ทันทีที่เจอ `。` หรือ `？` ตัวแรก ไม่ต้องรอจบบรรทัด หรือ cache เสียงของวลีที่ใช้บ่อย (edge-tts ใช้ ~0.65s แม้เป็นวลีสั้น)

ถ้าทำข้อ 1–3 คาดว่าเสียงประโยคเนื้อหาแรกจะอยู่ที่ ~3.5–4s ข้อ 4 ช่วยให้มีเผื่อ
