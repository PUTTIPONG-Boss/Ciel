# แนวทางทำให้ Ciel ตอบไวขึ้น — research + ทดลองบน Mac 2026-10-27

> ต่อจาก [2026-10-27-speed.md](2026-10-27-speed.md) (เรื่อง prompt cache และ keep_alive)
> เครื่อง: MacBook M1 (GPU 8 core, แบนด์วิดท์หน่วยความจำ ~68GB/s), RAM 16GB, Ollama 0.40.6

## สรุปสั้น

1. **เพดานของเครื่อง:** M1 รุ่นธรรมดาสร้างคำตอบได้ ~10–14 token/วินาที ไม่ว่าโมเดลจะเล็กแค่ไหน เปลี่ยนโมเดลจึงไม่ได้เร็วขึ้นมาก
2. **ทางที่ได้ผลจริง** คือไม่ให้เครื่องทำงานซ้ำ (prompt cache, keep_alive) กับให้ **เสียงแรกออกเร็ว** (ประโยคแรกสั้น และมีเสียงรับคำทันที)
3. **ใช้ `qwen3:8b` ต่อ** โมเดลที่ลองมาแทนเร็วขึ้นไม่คุ้ม หรือแย่กว่าในจุดสำคัญ

## ผลทดลองโมเดลอื่น (นิสัยแบบพูดน้อย)

| โมเดล | ตัวรัน | prompt (token) | สร้างคำตอบ | cache เมื่อเปลี่ยนคำถาม | ผล |
|---|---|---|---|---|---|
| `qwen3:8b` | llama.cpp | 3,043 | ~10 tok/s | ✅ ใช้ได้ (0.4s) | **ใช้ตัวนี้ต่อ** |
| `qwen3:4b` | llama.cpp | 3,043 | ~10 tok/s | ✅ | ❌ ปิดโหมดคิดไม่ได้ หลุดข้อความคิดภาษาอังกฤษ และวนพูดซ้ำไม่หยุด ข้อละ 4–8 นาที |
| `qwen3.5:4b-mlx` | **MLX** | 1,825 | ~14 tok/s | ❌ อ่าน prompt ใหม่ทั้งหมด (18s) | สร้างคำตอบเร็วขึ้นนิดหน่อย แต่ cache ใช้ไม่ได้ |
| `qwen3.5:4b-mtp-q4_K_M` | llama.cpp | 1,825 | ~9.5 tok/s | ❌ (10s) | MTP ไม่ได้ช่วย ไม่พบ log ว่ามี speculative decode ทำงาน |

ข้อสังเกต:
- **Qwen3.5 ใช้ token น้อยกว่า ~40%** สำหรับ prompt เดียวกัน (tokenizer ใหม่เก่งภาษาไทย/ญี่ปุ่นกว่า)
- แต่ Qwen3.5 เป็นโมเดลแบบไฮบริด (มีชั้นแบบ recurrent) Ollama จึงใช้ prompt cache ได้เฉพาะเมื่อ prompt **เหมือนเดิมทุกตัวอักษร** พอคำถามเปลี่ยน ต้องอ่านใหม่ทั้งหมด 10–18 วินาทีทุกข้อความ เสียเปรียบ `qwen3:8b` ที่แก้เรื่องนาฬิกาแล้วเหลือ 0.4 วินาที
- `qwen3:4b` สร้างคำตอบได้ ~10 tok/s เท่ากับ 8b แปลว่าคอขวดอยู่ที่เครื่อง ไม่ใช่ขนาดโมเดล

## แนวทางที่ research มา และความเหมาะกับ Ciel

### ✅ 1. ทำให้เสียงแรกออกเร็ว (ได้ผลมากสุดต่อความรู้สึกของผู้ใช้)

งานวิจัยเรื่อง voice agent ชี้ว่าผู้ใช้รับรู้ความเร็วจาก **เวลาจนได้ยินเสียงแรก** มากกว่าเวลาตอบจบ ([ConvFill](https://arxiv.org/html/2511.07397v1), [PACE](https://arxiv.org/pdf/2609.10372), [callin.io](https://callin.io/blogs/reduce-perceived-latency-in-ai-voice-agents))
Ciel พูดทีละบรรทัดอยู่แล้ว จึงใช้ได้ทันที 2 แบบ:

- **ประโยคแรกเป็นคำรับคำสั้นๆ (ปรับใน prompt ได้):** ให้บรรทัดแรกเป็น 相槌 ยาว 2–6 token เช่น `[calm]……はい。` / `[pout]……ふーん。` / `[shy]な、何ですか……。`
  ที่ 10 tok/s บรรทัดนี้เสร็จใน ~0.5 วินาที และเข้ากับนิสัยคูเดเระพอดี นิสัยแบบพูดน้อยทำแบบนี้อยู่แล้วในหลายตัวอย่าง ควรเขียนเป็นกฎให้ชัด
- **เสียงรับคำที่อัดไว้ล่วงหน้า (แก้ฝั่งเว็บหรือเซิร์ฟเวอร์):** พอผู้ใช้ส่งข้อความ ให้เล่นเสียงสั้นที่สร้างด้วย TTS เก็บไว้ก่อนแล้วทันที เช่น 「ん。」「はい。」 ระหว่างรอโมเดล ใช้เวลาเพิ่มเป็นศูนย์
  (แนวคิดเดียวกับ ConvFill/PACE ที่ใช้โมเดลเล็กพูดนำ แต่บน M1 ไม่ควรรันโมเดลเล็กเพิ่ม เพราะจะแย่งแบนด์วิดท์กับโมเดลหลัก)

### ✅ 2. ไม่ให้อ่าน prompt ซ้ำ (แก้แล้วได้ 10–35 วินาที)

ดู [2026-10-27-speed.md](2026-10-27-speed.md): ย้ายนาฬิกาไปไว้ในข้อความผู้ใช้ ใช้ `keep_alive: -1` และ warm-up ตอนเริ่มเซิร์ฟเวอร์

### ✅ 3. ตอบสั้น = เร็ว

ปิดโหมดคิด (`think: false`) อยู่แล้ว ส่วนที่เหลือคือจำนวน token ของคำตอบ การ "prompt ให้คิดเร็ว" จึงเท่ากับให้พูดสั้น (นิสัยแบบพูดน้อย) และเพิ่ม `num_predict` ประมาณ 150 ไว้กันวนพูดไม่หยุด

### ⚠️ 4. Speculative decoding / MTP (ใช้โมเดลเล็กเดาคำล่วงหน้า)

- หลักการ: โมเดลเล็กเดาหลาย token แล้วโมเดลใหญ่ตรวจทีเดียว ช่วยได้เมื่อคอขวดอยู่ที่แบนด์วิดท์ ซึ่งเป็นกรณีของ M1 ([Wikipedia](https://en.wikipedia.org/wiki/Speculative_decoding))
- Ollama ช่วงหลังรองรับ MTP head ในตัวโมเดลกับ draft model บางตัว ([Ollama releases](https://github.com/ollama/ollama/releases), [llmcheck](https://llmcheck.net/guides/ollama-mlx-mac/), [NexGPU](https://nexgpu.net/blog/en/archives/60/))
- แต่ได้ผลดีกับข้อความที่เดาง่าย (โค้ด) และได้ผลน้อยกับบทสนทนาเปิดกว้าง ([vucense](https://vucense.com/dev-corner/speculative-decoding-explained-2x-faster-local-llms-ollama-llama-cpp-2026/))
  และ Ciel ตอบสั้นแค่ 30–60 token อยู่แล้ว ทดลอง `qwen3.5:4b-mtp` บน Mac ไม่เห็นผล → **ยังไม่คุ้ม**

### ⚠️ 5. เปลี่ยนตัวรันเป็น MLX

MLX เร็วกว่า llama.cpp ในการสร้างคำตอบราว 5–20% บนชิปใหญ่ แต่บน M1 อ่าน prompt ช้ากว่า ([yage.ai](https://yage.ai/share/mlx-apple-silicon-en-20260331.html), [zachrattner](https://zachrattner.com/projects/ai-mac-cluster/mlx-vs-ollama), [towardsai](https://pub.towardsai.net/apples-mlx-runs-local-llms-3x-faster-than-llama-cpp-until-your-context-hits-40k-715ec441afbb?gi=663fd87322f7))
`qwen3:8b` ยังไม่มีเวอร์ชัน MLX ใน Ollama ส่วน `qwen3.5:4b-mlx` ได้ ~14 tok/s แต่ cache ใช้ไม่ได้ → **ยังไม่คุ้ม**

### ❌ 6. ใช้โมเดลย่อยหลายตัวช่วยคิด (router / แยกงาน)

ช่วยได้บนเซิร์ฟเวอร์ที่มีหลาย GPU แต่บน M1 ทุกโมเดลแย่งหน่วยความจำและแบนด์วิดท์เดียวกัน รันสองตัวพร้อมกันจะช้าลงทั้งคู่
ใช้ได้แค่แบบไม่ต้องใช้โมเดล คือเสียงรับคำที่อัดไว้ (ข้อ 1)

### 💡 7. ฮาร์ดแวร์

ความเร็วสร้างคำตอบแปรตามแบนด์วิดท์หน่วยความจำ M1 Pro/Max (200–400GB/s) เร็วกว่า M1 ธรรมดา 3–6 เท่าที่โมเดลเดิม ([insiderllm](https://insiderllm.com/guides/best-local-llms-mac-2026/), [starmorph](https://blog.starmorph.com/blog/apple-silicon-llm-inference-optimization-guide))

## ลำดับที่แนะนำให้ฝั่ง Windows ทำ

1. แก้ prompt cache + `keep_alive` + warm-up ตาม [2026-10-27-speed.md](2026-10-27-speed.md)
2. ใช้นิสัยแบบพูดน้อย ([ciel-concise-proposal.yaml](ciel-concise-proposal.yaml)) และเพิ่มกฎ "บรรทัดแรกเป็นคำรับคำสั้นๆ เสมอ" กับ `num_predict` ประมาณ 150
3. เล่นเสียงรับคำที่อัดไว้ทันทีที่ส่งข้อความ
4. แก้ `_detect_kind` ใน `ciel/speech.py` ตาม [2026-10-27-concise-prompt.md](2026-10-27-concise-prompt.md)

คาดว่าเสียงแรกจะออกภายใน ~1 วินาที (เสียงที่อัดไว้) และประโยคจริงประโยคแรกตามมาภายใน 1–2 วินาที

ยังไม่ได้วัด: เวลาของ TTS (edge-tts ใช้เน็ต) และเวลารวมแบบ end-to-end ในแอปจริง เพราะ WebSocket ต้องล็อกอิน
