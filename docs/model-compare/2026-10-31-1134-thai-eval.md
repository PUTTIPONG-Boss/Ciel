ตรวจด้วย `tokenizer.apply_chat_template` ของ `mlx-community/Qwen3-8B-4bit` (ตัวที่ mlx-lm ใช้ตอนเทรน):

- ตัวอย่างหลายรอบ 65/145 ชุด: template ของ Qwen3 **ลบ `<think>\n\n</think>\n\n` ออกจากคำตอบเก่า** เหลือเฉพาะคำตอบสุดท้าย (เช่น 2 คำตอบ แต่มี think block 1 ที่)
- แต่ `render_chatml` ในแอป (`ciel/llm.py`) **ใส่ `EMPTY_THINK` หน้าคำตอบทุกข้อใน history**
- → ตั้งแต่ข้อที่ 2 ของบทสนทนา โมเดลเห็น prompt ที่ไม่เคยเห็นตอนเทรน ซึ่งอาจเป็นส่วนหนึ่งที่ทำให้รูปแบบพัง (แต่ข้อแรกของบทสนทนาก็พังด้วย จึงไม่ใช่สาเหตุเดียว)
- ข้อเสนอ (ฝั่ง Windows): ให้ `build_dataset.py` เขียนข้อมูลเทรนเป็นข้อความที่ render ด้วย `render_chatml` เดียวกับแอป (รูปแบบ `text` หรือ `completions` ของ mlx-lm) แทนรูปแบบ `messages` จะได้ตรงกันทุก token

ข้อสังเกตอื่น:
- `--mask-prompt` กับข้อมูลหลายรอบ: mlx-lm คิด loss เฉพาะคำตอบสุดท้ายของแต่ละตัวอย่าง จึงเทรนจริง 145 คำตอบ ไม่ใช่ 166
- 145 คำตอบ × 3 รอบ ยังน้อยสำหรับรูปแบบที่ซับซ้อน (ญี่ปุ่น + เลขซับ + แท็ก) ถ้าแก้เรื่อง template แล้วยังพัง ค่อยเพิ่มข้อมูลเป็น 300+ ตามที่ฝั่ง Windows เสนอ

## ความเร็วระหว่างทดสอบ

- ปิด OrbStack ระหว่างทดสอบแล้ว (ตามที่มาสเตอร์อนุญาต) แต่โมเดลที่เทรนแล้วยังใช้เวลาเฉลี่ย **61–77 วินาทีต่อข้อ** (บางข้อ ~4–12 วินาที บางข้อ 140–190 วินาที) ส่วน `qwen3:8b` เฉลี่ย 8.5 วินาที ทั้งชุดใช้ 1 ชม. 28 นาที (10:07–11:35)
- สาเหตุน่าจะเป็น keep-warm ของ Ciel ที่โหลด `qwen3:8b` กลับเข้า RAM ทุก ~5 นาทีระหว่างที่ `eval_thai.py` ทดสอบโมเดลอื่น ทำให้มีสองโมเดลใน RAM อีกครั้ง (ข้อที่ช้ามาเป็นช่วงๆ ไม่ใช่ทุกข้อ) swap ใช้ ~2.5 GB
- ข้อเสนอ: หยุด Ciel ระหว่าง eval (`launchctl bootout …`) หรือให้ `eval_thai.py` บอก Ciel ให้พัก keep-warm
