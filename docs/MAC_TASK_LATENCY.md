## ถึง Claude

v0.3.1 นำข้อเสนอจาก `docs/model-compare/2026-10-27-speed-research.md` ไปใช้ครบแล้ว ได้แก่:

- ย้ายวันเวลาไปไว้ในข้อความผู้ใช้ เพื่อให้ prompt cache ใช้ได้
- `keep_alive: -1`, `num_predict: 150` และ warm-up ตอนเริ่มเซิร์ฟเวอร์
- นิสัยแบบพูดน้อย v3 และให้บรรทัดแรกเป็นคำรับคำสั้นๆ
- เสียงรับคำ ん。/はい。 ฝั่งเว็บ
- แก้ `_detect_kind`

งานนี้คือ **วัดเวลาจริงผ่านแอป** (WebSocket → qwen3:8b → TTS) แบบเดียวกับที่มือถือใช้ แล้วเทียบกับตัวเลขก่อนแก้ใน `2026-10-27-speed.md`

### 🎯 เป้าหมายของผู้ใช้

**ได้ยินประโยคเนื้อหาจริงประโยคแรกภายใน 4 วินาทีหลังกดส่ง** โดยไม่นับเสียงรับคำ ん。/はい。 ส่วนที่เหลือพูดต่อได้

- **v0.3.15 (ต่อจาก `2026-10-28-0244-latency.md`):**
  - **probe กลับไปสร้าง 16 token (1 ครั้ง ไม่ใช่ 2 ครั้งแบบตอนเริ่มเซิร์ฟเวอร์) และยังยกเลิกได้เมื่อมีข้อความเข้ามา** ทำการทดสอบ "ว่าง 20 นาทีแล้วคุยต่อในบทสนทนาเดิม" ซ้ำ ข้อความแรกหลังว่างต้องกลับมา ~0.8s (v0.3.13: 0.78s, v0.3.14: 2.52s) และดูราคา probe ต่อรอบใน `server.log` (คาด ~2.5s)
  - ส่งข้อความตรงจังหวะ probe ซ้ำแบบรอบก่อน (ทันที / หลัง 1s) ดูว่า first token เพิ่มเท่าไร
  - เอาตัวอย่าง "เมื่อกี้คุยอะไรกัน" ออกแล้ว (โมเดลลอกเรื่องชื่อโปรเจกต์) ถามคำถามนี้ซ้ำในรอบว่าง ดูว่าตอบเรื่องที่คุยจริงไหม
  - **ข้อ 12–13 ช้าผิดปกติรอบก่อน** (first token 6.4s, ~5.8 tok/s): ถ้าเกิดอีก ให้ดึง `server.log` ช่วงนั้นมาด้วย (มีคำขออื่นซ้อนไหม เช่น warm-up เบื้องหลังหลังตัดประวัติยังไม่จบ หรือ probe) และ `memory_pressure` / `vm_stat` ตอนนั้นถ้าเป็นไปได้
  - วัด `--turns 16` ตามปกติ

- ผลอยู่ที่ `docs/model-compare/<วันที่>-latency.md`
- ถ้าอยากเช็กเร็วๆ ก่อน รัน `--gap 5` ได้ แต่รายงานหลักต้องใช้ค่าเริ่มต้น 65 วินาที

## ขั้นที่ 4: สรุปให้ผู้ใช้ (ภาษาไทย)

- **ผ่านเป้า 4 วินาทีกี่ข้อ** และค่าเฉลี่ย/ค่าสูงสุดของ **เสียงประโยคเนื้อหาแรก**
- ค่าเฉลี่ยของ **ข้อความครบ** และ **เสียงครบ** พร้อมเทียบกับก่อนแก้
- ข้อที่ไม่ผ่าน ให้แยกให้ได้ว่าเวลาหมดไปกับอะไร: โมเดลเขียนบรรทัดยาวเกิน (ดูคอลัมน์ "สองบรรทัดแรก") หรือ TTS ช้า (ดู log)
- ข้อไหนช้าผิดปกติ และสาเหตุที่น่าจะเป็น โดยดูจาก `~/Library/Logs/Ciel.log` เช่น บรรทัด `TTS ok on attempt` ที่แปลว่า TTS ต้องลองใหม่
