## ถึง Claude

v0.3.1 นำข้อเสนอจาก `docs/model-compare/2026-10-27-speed-research.md` ไปใช้ครบแล้ว ได้แก่:

- ย้ายวันเวลาไปไว้ในข้อความผู้ใช้ เพื่อให้ prompt cache ใช้ได้
- `keep_alive: -1`, `num_predict: 150` และ warm-up ตอนเริ่มเซิร์ฟเวอร์
- นิสัยแบบพูดน้อย v3 และให้บรรทัดแรกเป็นคำรับคำสั้นๆ

งานนี้คือ **วัดเวลาจริงผ่านแอป** (WebSocket → qwen3:8b → TTS) แบบเดียวกับที่มือถือใช้ แล้วเทียบกับตัวเลขก่อนแก้ใน `2026-10-27-speed.md`

### 🎯 เป้าหมายของผู้ใช้

**ได้ยินประโยคเนื้อหาจริงประโยคแรกภายใน 4 วินาทีหลังกดส่ง** โดยไม่นับเสียงรับคำ ん。/はい。 ส่วนที่เหลือพูดต่อได้

- **v0.3.11: คำแปลมีเลขประโยค (`>> 1 …`)** เพื่อแก้ซับไม่ตรงประโยคญี่ปุ่น
  - **ตรวจคำแปลทุกบรรทัดในหัวข้อ "คำตอบเต็ม"** ว่าตรงกับประโยคญี่ปุ่นข้างบนไหม แล้วทำตารางเฉพาะบรรทัดที่ไม่ตรง (ประโยคญี่ปุ่น / ซับที่ได้ / ควรเป็น) เทียบกับ 5 บรรทัดในรายงาน 2211
  - เช็กว่าเลขไม่โผล่บนจอ (ซับในรายงานต้องไม่ขึ้นต้นด้วย `1 ` หรือ `2 `) และดูใน log ว่าโมเดลเขียนเลขครบทุกบรรทัดไหม
- **v0.3.10 (ต่อจาก `2026-10-27-2211-latency.md`): แก้ประวัติยาวทำให้ช้า**
  - ประวัติเกิน 20 ข้อความจะตัดเหลือ 10 ทีเดียวทันทีหลังตอบ แล้วให้ Ollama อ่านใหม่เบื้องหลัง (log: `history trimmed to 10 messages` ตามด้วย `warm-up done`)
  - **รอบนี้วัดด้วย `--turns 16`** (ประมาณ 18 นาทีที่ gap 65s) แล้วดูว่าข้อ 11–16 ยังเร็ว ~0.7s ไหม โดยเฉพาะข้อ 11 ที่ตามหลังการตัด
    ```bash
    cd ~/Ciel && .venv/bin/python scripts/measure_latency.py --turns 16
    ```
  - ดูใน `server.log` ว่าการอ่านเบื้องหลังหลังตัดใช้เวลาเท่าไร (ควรเสร็จก่อนข้อถัดไปมาถึง เพราะ gap 65s)
  - ถ้ามีเวลา ทดลอง gap สั้น (`--turns 16 --gap 5`) เพื่อดูกรณีพิมพ์ต่อทันทีหลังตัด
- **v0.3.9 (ต่อจาก `2026-10-27-2141-latency.md`):**
  - warm-up ยิงคำขอเล็กแบบ stream 16 token 2 ครั้ง **รอบนี้ให้ดูข้อแรกหลังรีสตาร์ท** (รอบ `--gap 5` ที่รันทิ้ง) ว่า prefill ลดจาก 2.17s ไหม และดู ms/token ใน `server.log` ของคำขอ warm-up ทั้ง 3 ครั้ง
  - ตัวอย่างเพิ่มเป็น 28 ชุด (รับคำชม/ให้กำลังใจหลายแบบ) ดูว่าข้อ "เธอน่ารักนะ" และ "สัมภาษณ์งาน" ยังลอกไหม
  - ความเร็วสร้างคำตอบ (tok/s) เทียบกับ v0.3.8 (~9.6 tok/s) เพราะ prompt ยาวขึ้นอีก (~5,800 token)
- **v0.3.8 (ต่อจาก `2026-10-27-2012-latency.md`): รอบนี้เน้นคุณภาพคำตอบ**
  - ตัวอย่างบทสนทนาเปลี่ยนเป็น 24 ชุด หัวข้อไม่ตรงกับคำถามในสคริปต์ และเพิ่มกฎห้ามลอก/ห้ามใช้ `お大事に` ผิดบริบท
  - **ดูว่ายังลอกตัวอย่างไหม:** เทียบคำตอบกับ `examples` ใน `persona/ciel.yaml` และกับประโยคที่ซ้ำในรายงานก่อนๆ (`三分遅刻です`, `当然です。マスター専属ですから。`, `命令です。`, `……一応、です。`)
  - ข้อสัมภาษณ์งานยังมี `お大事に` ไหม
  - **ดูว่าเร็วเท่าเดิมไหม:** prompt ยาวขึ้นเป็น ~5,500 token ยังต้องผ่าน 8/8 และดูความเร็วสร้างคำตอบ (tok/s ใน `ollama: … gen`) เทียบกับรอบก่อน
  - log ต้องเห็น `warm-up done` หลังอัปเดต (เกิดตอนเปิดหน้าเว็บ/ต่อ WebSocket ครั้งแรก เพราะแก้แค่ YAML เซิร์ฟเวอร์ไม่รีสตาร์ท) **ให้รอ warm-up เสร็จก่อนเริ่มวัด** โดยรัน `measure_latency.py --gap 5` ทิ้งไปหนึ่งรอบก่อน
- **v0.3.7 (ต่อจาก `2026-10-27-1907-latency.md`):**
  - warm-up ยิงคำขอที่สอง (ข้อความ "สวัสดี" + สร้าง 4 token) เพื่ออุ่น GPU สำหรับคำขอเล็ก
  - **รอบนี้อยากรู้:** ข้อแรก (สวัสดี) prefill ลดจาก 2.17s เหลือ ~0.65s ไหม และเสียงเนื้อหาแรกต่ำกว่า 4s ไหม → ถ้าได้ก็ผ่าน 8/8
  - log เปลี่ยนเป็น `ollama: prompt N tok, prefill …s` (N คือความยาว prompt ทั้งหมด) ให้ดูเวลา prefill และ `cached n_tokens` ใน `~/.ollama/logs/server.log` เหมือนรอบที่แล้ว
- **v0.3.6 (ต่อจาก `2026-10-27-1732-latency.md`):**
  - **ข้อแรกช้า (สวัสดี 4.9s):** ดึง log ของทุกข้อแล้วใส่ในรายงานเป็นตาราง
    ```bash
    grep -aE "reply timing|ollama: prompt|U\+FFFD" ~/Library/Logs/Ciel.log | tail -20
    ```
    `ollama: prefill N tok` คือจำนวน token ที่ไม่ได้มาจาก cache ถ้าข้อแรก N สูงกว่าข้ออื่นมาก แปลว่า cache ของ system prompt + ตัวอย่างหายไป (เช่น ถูกบทสนทนาอื่นทับ) ถ้า N ต่ำแต่ `first token` ยังช้า แปลว่าสาเหตุอยู่ที่อื่น
  - คำถามภาษาอังกฤษได้ซับอังกฤษแล้วหรือยัง (เวลาที่เติมหน้าข้อความมี `sub: English`)
  - มี warning `Ollama sent U+FFFD` ไหม กี่ครั้ง
- **v0.3.5 (ทำตามข้อเสนอ raw prompt ใน `2026-10-27-1538-latency.md`):**
  - `OllamaLLM` ใช้ `/api/generate` แบบ `raw: true` และสร้าง prompt ChatML เอง (`render_chatml` ใน `ciel/llm.py`)
  - **รอบนี้อยากรู้:** prefill ข้อ 2 ขึ้นไปคงที่ ~0.65–0.7 วินาทีไหม (วัดตรงกับ Ollama แบบที่ทำในรายงาน 1538 ได้ โดยใช้ `render_chatml`)
  - log ต้องเห็น `warm-up done (qwen3:8b, raw, HTTP 200)` และข้อแรกต้องไม่ cold
  - เช็กว่าคำตอบไม่หลุดเป็นโหมดคิด (ไม่มี `<think>` โผล่) และรูปแบบบรรทัดยังถูก
- **v0.3.4 (ทำตามข้อเสนอที่ 1 และ 3 ใน `2026-10-27-speech-gaps.md`):**
  - โมเดลเขียนประโยคญี่ปุ่นทั้งหมดก่อน แล้วค่อยเขียนคำแปล `>>` ตามลำดับ
  - **รอบนี้ดูคอลัมน์ "เงียบระหว่างประโยค" และ "พูดจบ" เป็นหลัก** เป้าคือช่วงเงียบไม่เกิน ~0.5 วินาที
  - เช็กด้วยว่าโมเดลยังเขียนสลับคู่แบบเดิมไหม (ดูใน log หรือรายงาน) และคำแปลครบทุกประโยคไหม
- **v0.3.3 (ทำตามข้อเสนอในรายงาน `2026-10-27-1502-latency.md`):**
  - โมเดลไม่เขียนบรรทัดรับคำแล้ว บรรทัดแรกเป็นประโยคเนื้อหาสั้นๆ ไม่เกินประมาณ 12 ตัวอักษร
  - ใส่แท็กอารมณ์เฉพาะตอนอารมณ์เปลี่ยน
  - **แก้ cache หลุดระหว่างข้อ:** เดิมเวลาถูกเติมหน้าข้อความล่าสุดแต่ไม่ถูกเก็บลง history ข้อความก่อนหน้าจึงเปลี่ยนทุกรอบ ตอนนี้เติมเวลาครั้งเดียวแล้วเก็บลง history ตามนั้น
  - **แก้ซับไทยตอนถามภาษาอังกฤษ:** เดิมเวลาเขียนเป็นภาษาไทย โมเดลจึงเห็นว่าข้อความเป็นภาษาไทย ตอนนี้ใช้รูปแบบ `[2026-10-27 Tue 15:10]`
  - **รอบนี้อยากรู้เพิ่ม:** prefill ข้อที่ 2 เป็นต้นไปยังเป็นประมาณ 1.27 วินาทีไหม ถ้ายังเป็น แปลว่า chat template ของ Qwen3 แสดงคำตอบเก่าไม่ตรงกับตอนที่สร้าง
- ตัวเลขหลักในรายงานคือแถว **"เสียงประโยคเนื้อหาแรก"** และบรรทัด **"ผ่านเป้า ≤ 4 วินาที: x/8 ข้อ"**

## ขั้นที่ 2: วัด (ประมาณ 10–12 นาที)

```bash
cd ~/Ciel && .venv/bin/python scripts/measure_latency.py
```

- สคริปต์ถามคำถาม 8 ข้อต่อเนื่องในบทสนทนาเดียวกัน โดยเว้นห่างกันข้อละ **65 วินาที** เพื่อให้เวลาข้ามนาทีทุกครั้ง ซึ่งเป็นกรณีที่ prompt cache เคยใช้ไม่ได้
- รันแบบ background ได้ ใช้เวลานานเพราะต้องรอช่วงห่าง
- ผลอยู่ที่ `docs/model-compare/<วันที่>-latency.md`
- ถ้าอยากเช็กเร็วๆ ก่อน รัน `--gap 5` ได้ แต่รายงานหลักต้องใช้ค่าเริ่มต้น 65 วินาที

## ขั้นที่ 3: ส่งรายงานกลับ

1. เปิดไฟล์รายงานแล้วเพิ่มหัวข้อ **"เทียบกับก่อนแก้"** ไว้ท้ายไฟล์ โดยดึงตัวเลขจาก `2026-10-27-speed.md`:
   - ข้อความห่างกันเกิน 1 นาที: เดิมประมาณ 18 วินาที
   - ข้อความแรกหลังพัก: เดิมประมาณ 43 วินาที
2. เขียนข้อสังเกตเพิ่มถ้ามี เช่น:
   - คำตอบไหนยังลอกตัวอย่าง (โดยเฉพาะ "สวัสดี")
   - คำถามภาษาอังกฤษได้ซับภาษาอังกฤษไหม
   - บรรทัดแรกเป็นคำรับคำสั้นจริงไหม
3. commit และ push:

```bash
cd ~/Ciel && git add docs/model-compare/ && git commit -m "Latency after v0.3.1 speed fixes" && git push
```

## ขั้นที่ 4: สรุปให้ผู้ใช้ (ภาษาไทย)

- **ผ่านเป้า 4 วินาทีกี่ข้อ** และค่าเฉลี่ย/ค่าสูงสุดของ **เสียงประโยคเนื้อหาแรก**
- ค่าเฉลี่ยของ **ข้อความครบ** และ **เสียงครบ** พร้อมเทียบกับก่อนแก้
- ข้อที่ไม่ผ่าน ให้แยกให้ได้ว่าเวลาหมดไปกับอะไร: โมเดลเขียนบรรทัดยาวเกิน (ดูคอลัมน์ "สองบรรทัดแรก") หรือ TTS ช้า (ดู log)
- ข้อไหนช้าผิดปกติ และสาเหตุที่น่าจะเป็น โดยดูจาก `~/Library/Logs/Ciel.log` เช่น บรรทัด `TTS ok on attempt` ที่แปลว่า TTS ต้องลองใหม่
